# arcade-cs2

Dockerized CS2 (Wingman) dedicated server using
[joedwards32/cs2](https://github.com/joedwards32/CS2), plus its
[arcade.stanley.arpa](https://github.com/jakestanley/homelab-arcade) control adapter — see
[`arcade/README.md`](arcade/README.md) for that half.

## Deployment model — this repo has no interactive checkout

Unlike `arcade-palworld`/`arcade-minecraft`, nothing here is meant to live on disk as a
human-managed clone with a `./scripts/up.sh` to run by hand. Every deploy — including the
very first one — is CI pushing to `main`. Think of the host the way you'd think about a
managed container platform: it's just compute Woodpecker happens to run on, not something
you `cd` into and maintain.

Concretely:
- **`.woodpecker/ci.yaml`** — on every push to `main`: rebuilds `arcade-adapter` (picking up
  whatever's current on `lib-arcade`'s `main`) and brings both services up.
- **`.woodpecker/refresh.yaml`** — every six hours: `docker compose pull` for `cs2` (picks up
  a new `joedwards32/cs2:latest` if one exists) and a fresh rebuild of `arcade-adapter` (picks
  up new `lib-arcade` commits), then `up -d`. Compose only actually recreates a service if
  what it resolved changed — no manual version comparison needed.

Both workflows run on the ordinary Docker-backed Woodpecker agent (`docker compose build`/
`up` work fine against the host's own Docker socket from inside a sandboxed step — confirmed,
not assumed). This repo needs to be marked **trusted** in Woodpecker for its `volumes:` (the
Docker socket mount) to actually be honored — `homelab-ci/scripts/add-repo.sh` sets this
during activation.

**Debugging**: there's no persistent local copy of this repo to read. `docker logs`/
`docker exec` work directly on the host same as any container. To actually read or edit the
code, `git clone` it into a scratch directory — the same way CI itself does, every run.

## Configuration

No `.env` file exists anywhere for this repo — see [`arcade/README.md`](arcade/README.md#config)
for why, and how config actually gets in. `.env.example` in this repo root is documentation of
what the two real secrets are, not something you copy to a real `.env`.

`SRCDS_TOKEN` is a Steam Game Server Login Token (GSLT), obtained from
[Steam's Game Server Account Management page](https://steamcommunity.com/dev/managegameservers)
for App ID 730 (CS2) — this has to be generated by a human with a Steam account, not something
that can be created programmatically.

## Data

The CS2 install (downloaded by SteamCMD on first boot) and any server-side state live in the
named Docker volume `cs2_data` — not a bind-mounted host path, since there's no stable
directory to bind to. This is what makes redeploys not re-download the entire game every time,
regardless of which ephemeral CI checkout triggered them.

## Config reference

Server settings (map, gamemode, bot difficulty, RCON, etc.) are set directly as literal
values in `docker-compose.yml`'s `cs2` service `environment:` block — see the
[image's documentation](https://github.com/joedwards32/CS2) for the full set of supported
`CS2_*`/`TV_*` variables.
